# Database setup and migrations

Migrations are generated by drizzle-kit from `src/lib/db/schema.ts` into `src/lib/db/migrations/`
(committed). `0000_init.sql` is the baseline: it creates every table, constraint and index, and enables
row-level security on each table (no policies, so Supabase's Data API denies anon/authenticated access;
the app connects as the table owner and is unaffected).

## New (empty) Supabase project

1. In `.env.local`, point `DATABASE_URL`/`MIGRATE_URL` (session pooler, port 5432), `NEXT_PUBLIC_SUPABASE_URL`
   and `SUPABASE_SERVICE_ROLE_KEY` at the new project.
2. Create the tables:

   ```bash
   npx drizzle-kit migrate
   ```

3. Create the storage buckets (`brand-assets` public, `order-images` private):

   ```bash
   node scripts/setup-storage.mjs
   ```

## Changing the schema later

Edit `src/lib/db/schema.ts`, then `npx drizzle-kit generate --name <change>`, review the SQL, commit it, and
run `npx drizzle-kit migrate` before deploying the code that depends on it.

## Existing database created before the baseline (legacy path)

A database that already has the old tables cannot run `0000_init.sql`, because its tables already exist.
Upgrade it with the hand-written, idempotent SQL in this folder instead:

| File | What it does |
| --- | --- |
| `0001_multi_service_applications.up.sql` | Adds the service catalog fields and the `paid` step to `applications` |
| `0001_multi_service_applications.down.sql` | Rolls 0001 back (destructive, see header) |
| `0002_enable_rls.up.sql` | Enables row-level security on the 8 app tables |
| `0002_enable_rls.down.sql` | Disables it again |

Then record the baseline as applied so `drizzle-kit migrate` starts from the next migration. Ask before
doing this on production. The record goes into `drizzle.__drizzle_migrations`, using the hash and `when`
values from `src/lib/db/migrations/meta/_journal.json`.
